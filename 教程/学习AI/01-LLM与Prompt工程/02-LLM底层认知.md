# 第一章：LLM 底层认知

> 📖 对应学习计划 **Day 1-2**。本章从底层原理出发，理解 LLM 怎么工作、为什么会产生幻觉、不同模型怎么选。

---

## 1.1 什么是大语言模型（LLM）

大语言模型的核心能力是**预测下一个 token**。给定一段文本，模型计算每个可能的下一个词的概率，选择最可能的那一个——然后把这个词加到输入中，继续预测下一个。

这个简单的机制，在超大规模（数千亿参数）和海量语料（万亿级 token）训练后，涌现出了推理、翻译、编程等复杂能力。

**关键认知**：LLM 不是数据库，不是搜索引擎，不是推理引擎。它是一个**概率性的文本补全系统**——理解这一点，才能理解它为什么会产生幻觉、为什么需要 Prompt 工程。

---

## 1.2 LLM 训练极简三阶段

不需要深入所有细节，理解这三个阶段就能建立正确的认知模型：

```
预训练（Pre-training）  →  监督微调（SFT）  →  人类反馈强化学习（RLHF）
「读完整个互联网」         「学做对话格式」        「学会什么是对的」
```

| 阶段 | 通俗解释 | 训练数据 | 产出 |
|------|---------|---------|------|
| **预训练** | 给模型喂万亿级 token 的文本，让它学会「下一个词是什么」 | 网页、书籍、代码、论文 | 基础模型（会补全，不会对话） |
| **监督微调（SFT）** | 用人工标注的「问题→理想回答」数据训练，教会模型对话格式 | 数万条人工标注的问答对 | 会聊天的模型 |
| **人类反馈强化学习（RLHF）** | 让人工对多个回答排序，模型学会「什么样的回答更好」 | 人工偏好标注 | 对齐后的模型（更像人类期望） |

> 💡 **为什么这很重要？** 预训练阶段的语料截止日期决定了模型的「知识边界」——它无法知道训练数据截止日期之后的事情。这就是为什么你需要 Context7 MCP 注入最新文档。

### 涌现能力（Emergent Abilities）

当模型参数达到一定规模（通常在 10B+ 参数），会突然出现小模型完全不具备的能力——且这些能力不是被「设计」出来的，而是自然涌现的：

| 涌现能力 | 表现 | 出现规模 |
|---------|------|---------|
| **上下文学习（In-Context Learning）** | 不更新权重，仅通过 Prompt 中的示例学会新任务 | ~10B |
| **思维链推理（CoT）** | 能「写出」多步推理过程 | ~100B |
| **指令遵循** | 理解并执行复杂的多约束指令 | ~10B |
| **代码生成与调试** | 从自然语言描述生成可运行代码 | ~10B |
| **工具使用** | 理解函数签名并正确调用外部工具 | ~100B |

> ⚠️ **关键推论**：涌现能力的阈值效应意味着——7B 模型和 70B 模型的能力差距不是线性的，而是质的飞跃。本地部署 7B 模型只能处理简单任务。

### 规模定律（Scaling Laws）

2020 年 OpenAI 提出了一个影响深远的发现：**模型性能与计算量、数据量、参数量呈幂律关系**。简单说：

- 更大的模型 + 更多的数据 + 更多的算力 = **可预测地更好**
- 不存在明显的上限——只要继续投入，性能就会继续提升
- 但边际效益递减：性能翻倍需要 10 倍计算资源

这就是为什么各大公司都在疯狂扩大模型规模——这条路在物理上还没有走到头。

## 1.3 Transformer 极简原理

不需要数学推导，只需理解三个核心概念：

| 概念 | 一句话解释 | 对编程的影响 |
|------|-----------|------------|
| **自注意力（Self-Attention）** | 每个词「看到」句子中所有其他词，计算关联强度 | 模型能理解长距离依赖（如函数调用关系） |
| **多层堆叠** | 注意力层反复叠加（几十到上百层） | 浅层学语法，深层学语义，最深层学推理 |
| **位置编码** | 给每个 token 标位置（第 1 个、第 2 个……） | 代码顺序至关重要——模型对代码位置敏感 |

> 📖 如需深入理解，推荐阅读 Jay Alammar 的《The Illustrated Transformer》（图文并茂，无数学公式）。

---

## 1.4 上下文窗口与 Token 机制

**Token 是什么**：LLM 处理的不是「字」，而是 token——文本被切分后的最小处理单元。

```
中文：1 个汉字 ≈ 1.5-2 个 token
英文：1 个单词 ≈ 1.3 个 token
代码：因语言而异，Python 约 1 个词 ≈ 1 token
```

**上下文窗口**：模型一次能「看到」的最大 token 数量。超过窗口的内容会被遗忘。

| 模型 | 上下文窗口 | 代码场景建议 |
|------|-----------|------------|
| Claude Opus 4 | 200K token | 完整项目级分析 |
| GPT-5 | 128K token | 多文件开发 |
| DeepSeek V3 | 128K token | 性价比之选 |
| Qwen 2.5 | 128K token | 国内替代方案 |
| Gemini 2.5 Pro | 1M token | 超大代码库分析 |

**Token 消耗的实战经验**：
- 一次完整的 Claude Code 会话通常消耗 10K-50K token
- 复杂多文件重构可能消耗 100K+ token
- `/compact` 命令可以压缩上下文，保留关键信息，节省约 40-60% token

## 1.5 模型幻觉：成因、识别与抑制

**幻觉（Hallucination）** 是 LLM 最核心的缺陷之一。模型**不是故意撒谎**——它只是在做概率补全时，「猜」出了一个看起来合理但事实上错误的内容。

### 四种幻觉类型

| 类型 | 表现 | 例子 |
|------|------|------|
| **事实性幻觉** | 编造不存在的 API/参数/文档 | 调用 `fs.rmSync(dir, {force: true})`——实际没有 `force` 选项 |
| **逻辑性幻觉** | 推理过程看似合理，结论错误 | Bug 分析头头是道，但指出的代码行根本没被调用 |
| **一致性幻觉** | 同一会话前后矛盾 | 第 3 条消息说用 React 18，第 8 条消息导入 React 16 的 API |
| **省略性幻觉** | 跳过关键步骤，声称完成 | 数据库迁移「完成」，但静默跳过了 14% 的记录 |

### 抑制幻觉的 6 个方法

1. **Spec-Driven 开发**：提供精确的接口文档/类型定义，减少模型「脑补」空间
2. **Context7 MCP**：注入最新版本框架文档，防止模型用过时的 API
3. **约束性 Prompt**：明确要求「不确定的内容直接告知，禁止编造」
4. **Few-shot 示例**：给 2-3 个正确示例，校准输出格式
5. **自我验证**：要求 AI 写完代码后自己验证（跑测试/检查类型）
6. **Rule 规则约束**：在 CLAUDE.md 中写明「幻觉约束」规则（见第 2 周教程）

## 1.6 开源 vs 闭源模型选型

**码农选模型，核心看四个维度**：

| 维度 | 说明 |
|------|------|
| **代码能力** | 代码生成质量、Bug 修复准确率、跨文件理解能力 |
| **上下文窗口** | 能同时分析的代码量 |
| **成本** | API 价格（每百万 token） |
| **可用性** | 国内直连、数据合规、API 稳定性 |

### 编程场景模型推荐

| 场景 | 推荐模型 | 理由 |
|------|---------|------|
| **复杂架构/大型重构** | Claude Opus 4 | 200K 上下文，代码质量 9.7/10 |
| **日常编码/快速迭代** | DeepSeek V3 / Claude Sonnet 4 | 性价比最优，质量不差 |
| **国内直连/免费** | DeepSeek V3 / Qwen 2.5 | 无需代理，中文理解 95%+ |
| **代码审查/Bug 定位** | Claude Opus 4 / GPT-5 | 逻辑推理最强 |
| **批量自动化** | OpenAI Codex（GPT-5 后端） | Token 效率约为 Claude Code 的 4 倍 |
| **本地私有化** | DeepSeek-Coder-7B / Qwen2.5-Coder-7B | 断网可用，零成本 |

### Token 效率 ≠ 模型能力

一个容易被忽略的维度是 **Token 效率**。不同模型生成同等质量代码消耗的 token 量差异巨大：

| 模型 | Token 效率 | 说明 |
|------|-----------|------|
| OpenAI Codex（GPT-5 后端） | ⭐⭐⭐⭐⭐ | 约为 Claude Code 的 4 倍，适合批量任务 |
| Claude Opus 4 | ⭐⭐⭐⭐ | 单次质量最高，但 token 消耗较大 |
| DeepSeek V3 | ⭐⭐⭐ | 中文场景效率高，成本优势明显 |

> 💡 **实战策略**：Codex 做审查 + Debug（效率高），Claude Code 做架构 + 初始功能（推理深）。两者互补而非二选一。详见 [[Wiki/wiki/topics/ai-coding-tools-comparison|AI Coding 工具全景对比]]。

### 推理模型（o1/o3/DeepSeek-R1）的选型注意

2025-2026 年出现了一类新的「推理模型」——它们内部会进行长时间的思维链推理，然后再输出答案。对于这类模型：

- **不要**写「请一步一步思考」——它们内部已经在做了
- **不要**用 Few-shot 示例——可能反而限制内部推理
- **要**简洁陈述问题，明确定义输出格式
- **要**用分隔符清晰划分输入段落

### 实战产出：《程序员大模型选型手册》

完成本章学习后，你应该能产出一份类似下面的选型决策表：

```
我当前项目：Next.js 全栈应用，50+ 文件，主要用 TypeScript
主力模型：Claude Sonnet 4（200K 上下文覆盖全项目）
降本方案：DeepSeek V3（日常小改动用，成本低 80%）
本地兜底：Qwen2.5-Coder-7B（断网或 API 故障时切换）
效率补刀：Codex（批量重构 / 代码审查场景，token 效率 4 倍）
```
