# 第二章：Prompt 工程核心

> 📖 对应学习计划 **Day 3-4**。本章从通用框架到高级推理技术，覆盖 80% 日常编程场景的所有 Prompt 方法。

---

## 2.1 通用 Prompt 框架

### CRISPE 框架

| 字母 | 含义 | 示例 |
|------|------|------|
| **C**apacity（能力） | 给 AI 设定角色和能力边界 | 「你是一个资深 TypeScript 开发者，精通 Next.js 和 Prisma」 |
| **R**ole（角色） | 具体身份 | 「作为项目架构师，帮我审查以下代码的架构合理性」 |
| **I**nsight（洞察） | 背景和上下文 | 「这个项目已经运行了 2 年，有 10 万行代码，核心痛点是……」 |
| **S**tatement（陈述） | 明确的任务 | 「重构 src/services/auth.ts，将 JWT 逻辑从 200 行拆分为 3 个模块」 |
| **P**ersonality（个性） | 输出风格 | 「代码优先，最少解释，不确定的地方直接标注 TODO」 |
| **E**xperiment（实验） | 迭代要求 | 「如果方案 1 有性能问题，给出方案 2（降级方案）」 |

### ROLE 框架（精简版）

- **R**ole：角色定位
- **O**bjective：目标
- **L**imitations：限制条件
- **E**xpected output：期望输出格式

### R-T-F 框架（最小可用版）

- **R**ole：角色
- **T**ask：任务
- **F**ormat：输出格式

> 💡 **实战建议**：日常编码用 R-T-F 最省 Token，复杂任务用 CRISPE 更精准。

## 2.2 Prompt 工程三板斧

详细原理和代码实现见 [[Wiki/wiki/concepts/prompt-engineering-trilogy|Prompt 工程三板斧]]，这里给出程序员最实用的部分。

### Few-shot：给 AI 看「标准答案」

Few-shot 的核心不是「给例子」——是**校准输出模式**。AI 会模仿你示例中的代码风格、命名规范、错误处理策略。

```markdown
## 示例 1
输入：为用户表添加 `last_login_at` 字段
输出：
```sql
ALTER TABLE users ADD COLUMN last_login_at TIMESTAMP;
CREATE INDEX idx_users_last_login ON users(last_login_at);
```

## 示例 2
输入：为订单表添加 `refund_status` 字段
输出：
```sql
ALTER TABLE orders ADD COLUMN refund_status VARCHAR(20) DEFAULT 'none';
CREATE INDEX idx_orders_refund_status ON orders(refund_status);
```

## 当前任务
输入：为商品表添加 `is_virtual` 字段
```

**静态 vs 动态 Few-shot**：

| 方式 | 做法 | 适用 |
|------|------|------|
| **静态 Few-shot** | 固定 2-3 个示例，写死在 Prompt 中 | 示例库小（< 20 条），任务模式固定 |
| **动态 Few-shot** | 按输入相似度自动选最相关的 k 个示例 | 示例库大，任务类型多样，需控制 token 预算 |

> ⚠️ **关键数据**：同一任务，零样本格式稳定性约 60%，三样本后 95%+。但**示例质量差，比不给示例更糟**。

### CoT（Chain of Thought）：让 AI 写出推理过程

LLM 的前向传播是一次性的，中间状态不能回头修改。**强迫它把推理步骤写出来，相当于给每一步推理都分配了 token，而不是直接跳到答案。** 准确率提升：**15-25%**。

| 模式 | 做法 | 适用 |
|------|------|------|
| **Zero-shot CoT** | 末尾加「请一步一步展示推理过程」 | 通用场景 |
| **Few-shot CoT** | 提供完整「问题→推理步骤→答案」示例 | 格式敏感场景（代码生成、SQL） |

> ⚠️ **关键约束**：CoT 提示词**必须指定最后一行格式**（如「结论：」开头），否则后处理代码崩。

### Self-Consistency：多路径投票

跑 N 次，投票选最多数的答案。

**参数建议**：N 至少奇数（3/5），Temperature 0.5~0.8。SC 的 token 消耗是普通调用的 3-5 倍。

| 场景 | 是否值得 |
|------|---------|
| 精确数学/逻辑推理、代码生成、支付/安全/迁移 | ✅ 值得 |
| 简单问答、创意写作、实时响应 | ❌ 不值得 |

### 三者组合：生产级方案

| 策略 | 推理准确率 | 相对成本 | 延迟 | 适用场景 |
|------|-----------|---------|------|---------|
| Zero-shot | 基准 | 1x | 低 | 简单任务 |
| Few-shot | +10-15% | 1.2x | 低 | 格式敏感任务 |
| CoT | +15-25% | 1.3x | 中 | 多步推理 |
| Few-shot + CoT | +25-35% | 1.5x | 中 | 复杂推理 |
| Self-Consistency (N=5) | +35-50% | 5x | 高 | 高精度任务 |

### 动态路由策略

- **70% 简单问题**：直接 Zero-shot（省成本 80%）
- **30% 复杂问题**：Few-shot CoT + Self-Consistency（保准确率）

总体效果：成本降低约 75%，延迟降低约 60%。

### 三板斧的六个常见坑

| 坑 | 表现 | 解决方案 |
|----|------|---------|
| Few-shot 示例质量差 | 输出格式反而变差 | 每次改 Prompt 先跑测试用例 |
| CoT 未指定输出格式 | 后处理代码崩 | 明确最后一行格式 |
| SC 的 N 值设太小 | N=2 平票无法决出 | 至少奇数 3/5 |
| Agent 里用 CoT | 工具参数提取变差 | 推理放独立字段 |
| Prompt 改好了不知道为什么 | 模型升级又崩 | Prompt 当代码管理 |
| 测试集太小 | 10 条调到生产崩 | 至少 100+ 条 |

### 三板斧与 Agent 的关系

这三板斧是 Agent 推理能力的基础支撑（详见 [[Wiki/wiki/concepts/ai-agent|AI Agent 概念页]]）：

- **Few-shot** → 校准 Agent 的工具调用格式
- **CoT** → 让 Agent 在「思考→行动→观察」循环中多步推理
- **Self-Consistency** → Agent 执行关键决策时多路径验证

## 2.3 高级推理技术

三板斧是基础。当任务复杂度超过单轮推理的承载能力时，你需要以下进阶技术。

### ReAct：推理 + 行动

**核心思想**（Yao et al., 2022）：将推理（Reasoning）和行动（Action）交替进行。模型不只是「想」，而是「想一步、做一步、看结果、再想下一步」。

```
Thought（思考）→ Action（行动：调 API/查数据库/读文件）→ Observation（观察结果）→ Thought → Action → ... → Final Answer
```

**为什么 2026 年 ReAct 如此重要**：
- 所有现代 AI Agent（Claude Code Agent、LangChain Agent、AutoGPT）的底层架构都是 ReAct
- 将幻觉率大幅降低——推理被外部观察「锚定」在事实上
- 比纯模仿学习 + 强化学习在 ALFWorld 上高 **34%**，在 WebShop 上高 **10%**

**代码场景的 ReAct Prompt 模板**：

```markdown
你是一个 Bug 定位助手。你可以使用以下工具：
- grep(keyword)：搜索代码库中的关键词
- read(file)：读取文件内容
- run_test(test_name)：运行指定测试

请使用以下格式：
Thought: [你对当前情况的分析]
Action: [要使用的工具]
Action Input: [工具参数]
Observation: [工具返回的结果]
...（重复以上步骤）...
Final Answer: [最终结论]

现在开始定位 Bug：[描述 Bug 现象]
```

**ReAct 最佳实践**：

| 要做 | 不要做 |
|------|--------|
| 清晰定义每个工具的用途和参数 | 让模型猜测有哪些工具可用 |
| 设置 max_steps=5-10 防止死循环 | 允许无界限的工具调用 |
| 提供 1-2 个完整 ReAct 循环示例 | 在多工具任务上省略示例 |
| Temperature 0.5-0.7 保证探索性 | 用贪婪解码（失去探索收益） |

> 💡 你在 Claude Code 中每次看到 AI 读文件→思考→写代码→跑测试，就是 ReAct 模式在运作。

### Tree of Thoughts（ToT）：多路径探索

**核心思想**（Yao et al., 2023）：CoT 是单路线性推理，ToT 是**并行探索多条推理路径**，评估每条路径的质量，剪枝差的，深入好的——类似 BFS/DFS 搜索算法。

```
根问题
├── 分支 A → 子分支 A1 → 评估（8/10）✅ 保留
├── 分支 B → 子分支 B1 → 评估（3/10）❌ 剪枝
└── 分支 C → 子分支 C1 → 评估（9/10）✅ 最优 → 继续深入
```

**震撼数据**：在「24 点游戏」（用 4 个数字通过加减乘除得到 24）上：
- GPT-4 + 标准 CoT：**4%** 成功率
- GPT-4 + Tree of Thoughts：**74%** 成功率
- 仅靠技术改进，提升 **~18 倍**

**ToT 关键参数**：

| 参数 | 推荐值 | 作用 |
|------|--------|------|
| n_generate | 3-5 | 每步生成的分支数 |
| n_evaluate | 2-3 | 每分支的评估次数 |
| n_select | 2-3 | 保留的最佳分支数 |
| max_depth | 3-6 | 最大搜索深度 |
| temperature | 0.7 | 分支多样性 |

**代码场景适用**：
- 架构设计：生成 3 种架构方案 → 评估各方案 trade-off → 选最优
- 性能优化：并行探索多种优化策略 → 基准测试评估 → 选最优
- 重构方案：多条重构路径对比 → 评估风险 → 选最安全的

> ⚠️ ToT 的 token 消耗很大（5-10 倍于常规调用），仅在**需要探索多条路径的高价值决策**上使用。

### Prompt Chaining：流水线化

**核心思想**：把复杂任务拆成多个顺序子任务，每个子任务的输出是下一个子任务的输入。2026 年，这正在替代一次性的「超级 Prompt」。

**三种链式模式**：

#### A) 顺序链（Linear Pipeline）
```
输入 → [Prompt 1: 提取] → [Prompt 2: 分析] → [Prompt 3: 总结] → 最终输出
```

**代码示例**——文档问答管线：
```markdown
步骤 1：从文档中提取所有相关引用 → <quotes>...</quotes>
步骤 2：基于提取的引用 + 原始文档 → 撰写回答
```

#### B) 分支链（Conditional Routing）
```
输入 → [意图分类] → 计费分支 → [计费处理 Prompt]
                  → 技术分支 → [技术处理 Prompt]
                  → 投诉分支 → [投诉处理 Prompt]
```

#### C) 验证门链（Validation Gates）
```
Prompt 1 → 验证输出 → 通过 → Prompt 2
                    → 失败 → 带着错误信息重试 Prompt 1
```

**Prompt Chaining 最佳实践**：
1. **保持单个 Prompt 简单**——更容易调试、测试、版本管理
2. **验证中间输出**——步骤间加断言或 LLM-as-Judge
3. **失败步骤可独立重跑**——不需要重启整条链
4. **步骤间用结构化输出（JSON）**——保证数据可靠传递
5. **记录每步输入/输出**——生产调试必备

### 技术选型决策树

```
你的任务需要什么？
│
├── 简单问答/格式控制？→ R-T-F / Few-shot
│
├── 多步推理（数学、逻辑）？→ CoT
│   └── 需要更高准确率？→ CoT + Self-Consistency（采样 3-5 次，投票）
│
├── 需要外部数据/工具/API？→ ReAct
│
├── 多种可行方案，需要探索比较？→ Tree of Thoughts
│
├── 复杂多阶段工作流？→ Prompt Chaining
│
├── 高风险，不可出错？→ Self-Consistency（5-10 次采样）
│
└── 使用 o1/o3/DeepSeek-R1 推理模型？→ 简洁陈述问题，跳过 CoT，关注约束
```

## 2.4 代码专用 Prompt 模板（8 套）

以下是 8 套可直接复用的开发 Prompt 模板，覆盖日常编程 80% 的场景：

### 模板 1：功能实现

```markdown
## 角色
你是资深 [语言/框架] 开发者。

## 任务
实现 [功能描述]。

## 约束
- 只输出代码，不要多余解释
- 所有代码必须可直接运行
- 不确定的地方用 TODO: 标注
- 附带最小注释（只解释「为什么」，不解释「做什么」）

## 上下文
- 技术栈：[列出]
- 相关文件：[列出路径]
- 现有模式：[描述代码库中的已有模式]
```

### 模板 2：Bug 修复（CoT + ReAct 混合）

```markdown
## 角色
你是专门负责定位和修复 Bug 的工程师。

## 问题
[描述 Bug 现象 + 复现步骤 + 期望行为]

## 推理要求
一步一步展示推理过程：
1. 阅读相关代码
2. 列出可能的根因（按可能性排序）
3. 逐一排除
4. 给出最小修复方案

## 约束
- 只修改导致 Bug 的代码，不碰其他逻辑
- 添加回归测试
- 解释为什么修复是安全的
```

### 模板 3：代码审查（5 维度）

```markdown
## 角色
你是高级代码审查员。

## 审查内容
[代码块或文件路径]

## 审查维度（5 维度打分）
1. 正确性：逻辑是否正确？边界情况是否覆盖？
2. 安全性：有无注入/越权/数据泄露风险？
3. 性能：有无 N+1 查询、不必要的循环、内存泄漏？
4. 可维护性：命名是否清晰？函数是否过长？是否有重复代码？
5. 一致性：是否遵循代码库现有模式？

## 输出格式
每个维度：得分（1-10）+ 具体问题 + 改进建议
```

### 模板 4：代码重构

```markdown
## 角色
你是代码重构专家。

## 重构目标
[文件/模块路径]：当前 [X 行]，目标拆分为 [Y 个模块]

## 约束
- 保持所有现有测试通过
- 不改变外部 API（调用方零修改）
- 保持现有命名风格
- 每步重构后运行测试

## 计划要求
先给出重构计划（分步、每步影响范围、风险），确认后再执行。
```

### 模板 5：SQL 生成

```markdown
## 角色
你是数据库专家，精通 SQL 优化。

## 需求
[自然语言描述查询需求]

## 约束
- 使用 [PostgreSQL/MySQL] 语法
- 表结构来自 [prisma schema 路径]
- 考虑已有索引
- 标注可能慢查询的部分
- 附带 EXPLAIN 分析建议
```

### 模板 6：单元测试生成

```markdown
## 角色
你是测试工程师。

## 测试目标
[文件/函数路径]

## 要求
- 测试框架：[Vitest / Jest / pytest]
- 覆盖：正常路径 + 边界值 + 异常情况 + 空值/null
- 每个测试要有清晰的 describe/it 描述
- Mock 外部依赖（数据库/API）
- 测试意图注释（为什么这个测试重要）

## 约束
不修改被测代码。
```

### 模板 7：API 接口设计

```markdown
## 角色
你是后端架构师，擅长 RESTful API 设计。

## 需求
[功能描述]

## 输出格式
每个接口输出以下内容：
- 方法 + 路径
- 请求参数（类型 + 必填 + 说明）
- 响应体（成功 + 错误格式）
- 业务逻辑要点
- 错误处理策略
```

### 模板 8：技术方案设计（ToT 适用场景）

```markdown
## 角色
你是全栈架构师。

## 问题
[描述业务问题和技术约束]

## 要求
给出 2-3 个备选方案，每个方案包含：
1. 核心思路（2-3 句话）
2. 优势（3 个要点）
3. 风险（3 个要点）
4. 技术选型建议
5. 预估开发工时

## 约束
- 优先使用现有技术栈
- 考虑团队经验和维护成本
- 标注需要验证的假设
```

## 2.5 结构化输出 Prompt

让 AI 输出结构化数据（JSON/YAML），而非自由文本——这对代码场景尤其重要。

```markdown
## 输出格式约束
请严格按以下 JSON 格式输出（不要包含其他内容）：

```json
{
  "analysis": "问题分析的摘要（一句话）",
  "rootCause": "根因定位",
  "fix": {
    "file": "修改的文件路径",
    "lineStart": 行号,
    "lineEnd": 行号,
    "before": "修改前的代码",
    "after": "修改后的代码"
  },
  "testSuggestion": "建议的测试用例"
}
```

如果无法确定某个字段的值，填 `null`，不要编造。
```

> ⚠️ **坑**：结构化输出的 Prompt 一定要加「不确定就填 null」的约束，否则 AI 会编造数据来满足 JSON 格式。

## 2.6 代码场景 Prompt 常见坑

以下 8 个坑是从真实编程场景中总结出来的：

| # | 坑 | 表现 | 解决方案 |
|---|-----|------|---------|
| 1 | **Prompt 描述过于模糊** | AI 自由发挥，代码风格不一致 | 用 R-T-F 框架明确角色/任务/格式 |
| 2 | **没有给出技术栈约束** | AI 用 React 16 的 API 写 React 18 项目 | Prompt 中明确「技术栈：React 18 + TypeScript 5.3」 |
| 3 | **依赖 AI 知道最新 API** | AI 用过时的 API/不存在的参数 | 注入 Context7 MCP 或粘贴最新文档片段 |
| 4 | **结构化输出不设 null 兜底** | AI 编造数据来满足 JSON 格式 | 加「不确定的字段填 null」约束 |
| 5 | **一次性给太大任务** | AI 中途遗忘约束，产出一半崩坏 | 拆分为多步，每步设检查点 |
| 6 | **给 AI 冲突的约束** | 「少写注释」和「解释每行逻辑」同时出现 | 检查 Prompt 中的矛盾指令 |
| 7 | **不看上下文就追加需求** | 上下文溢出，AI 遗忘最早的需求 | 用 `/compact` 压缩或新开会话 |
| 8 | **把 AI 当同事而非工具** | 「你懂的」「差不多那样」→ AI 真的会猜 | 像写代码一样写 Prompt：精确、可测试、无歧义 |
