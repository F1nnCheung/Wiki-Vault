# LLM 与 Prompt 工程学习指南

> 对应学习计划**第 1 周**：搞懂大模型运行逻辑，精通程序员专属 Prompt 写法，解决 AI 代码幻觉、输出不规范问题。

---

## 核心认知

**Prompt 是程序员与 AI 的「编程语言」。写好 Prompt 的本质，是把模糊的意图转化为 AI 无法误解的精确指令。**

在第 2 周你将学到 Rule（约束 AI 的行为规范）和 Skills（教 AI 怎么思考的方法论包）。三者分层协同：

```
LLM 底层认知（理解 AI 怎么工作）
  ↓  决定你能写出多精准的 Prompt
Prompt 工程（告诉 AI「这次做什么」）
  ↓  具体指令 + 输出格式 + 推理路径
Rule 约束层（告诉 AI「在这个项目里怎么做事」）  ← 第 2 周
  ↓  定义边界和规范，每次会话自动注入
Skills 方法论层（教 AI「遇到某类问题怎么思考」）  ← 第 2 周
  ↓  被 AI 自动发现、按需调用
```

**为什么 Prompt 工程对程序员至关重要？** 因为 LLM 不是数据库、不是搜索引擎、不是推理引擎——它是一个**概率性的文本补全系统**。你不给它精确的上下文和约束，它就会「脑补」——这就是幻觉的根源。好的 Prompt 本质上是**压缩不确定性**：用格式约束减少输出方差，用推理路径提升逻辑准确率，用示例校准行为模式。

> 💡 把 Prompt 当成代码来写：有版本、有测试、有回滚。详见第三章「Prompt 版本管理与测试」。

## 第一章：LLM 底层认知

> 📖 本章对应学习计划 Day 1-2。

### 1.1 什么是大语言模型（LLM）

大语言模型的核心能力是**预测下一个 token**。给定一段文本，模型计算每个可能的下一个词的概率，选择最可能的那一个——然后把这个词加到输入中，继续预测下一个。

这个简单的机制，在超大规模（数千亿参数）和海量语料（万亿级 token）训练后，涌现出了推理、翻译、编程等复杂能力。

**关键认知**：LLM 不是数据库，不是搜索引擎，不是推理引擎。它是一个**概率性的文本补全系统**——理解这一点，才能理解它为什么会产生幻觉、为什么需要 Prompt 工程。

### 1.2 Transformer 极简原理

不需要数学推导，只需理解三个核心概念：

| 概念 | 一句话解释 | 对编程的影响 |
|------|-----------|------------|
| **自注意力（Self-Attention）** | 每个词「看到」句子中所有其他词，计算关联强度 | 模型能理解长距离依赖（如函数调用关系） |
| **多层堆叠** | 注意力层反复叠加（几十到上百层） | 浅层学语法，深层学语义，最深层学推理 |
| **位置编码** | 给每个 token 标位置（第 1 个、第 2 个……） | 代码顺序至关重要——模型对代码位置敏感 |

> 📖 如需深入理解，推荐阅读 Jay Alammar 的《The Illustrated Transformer》（图文并茂，无数学公式）。

### 1.3 上下文窗口与 Token 机制

**Token 是什么**：LLM 处理的不是「字」，而是 token——文本被切分后的最小处理单元。

```
中文：1 个汉字 ≈ 1.5-2 个 token
英文：1 个单词 ≈ 1.3 个 token
代码：因语言而异，Python 约 1 个词 ≈ 1 token
```

**上下文窗口**：模型一次能「看到」的最大 token 数量。超过窗口的内容会被遗忘。

| 模型 | 上下文窗口 | 代码场景建议 |
|------|-----------|------------|
| Claude Opus 4 | 200K token | 完整项目级分析 |
| GPT-5 | 128K token | 多文件开发 |
| DeepSeek V3 | 128K token | 性价比之选 |
| Qwen 2.5 | 128K token | 国内替代方案 |
| Gemini 2.5 Pro | 1M token | 超大代码库分析 |

**Token 消耗的实战经验**：
- 一次完整的 Claude Code 会话通常消耗 10K-50K token
- 复杂多文件重构可能消耗 100K+ token
- `/compact` 命令可以压缩上下文，保留关键信息，节省约 40-60% token

### 1.4 模型幻觉：成因、识别与抑制

**幻觉（Hallucination）** 是 LLM 最核心的缺陷之一。模型**不是故意撒谎**——它只是在做概率补全时，「猜」出了一个看起来合理但事实上错误的内容。

**四种幻觉类型**：

| 类型 | 表现 | 例子 |
|------|------|------|
| **事实性幻觉** | 编造不存在的 API/参数/文档 | 调用 `fs.rmSync(dir, {force: true})`——实际没有 `force` 选项 |
| **逻辑性幻觉** | 推理过程看似合理，结论错误 | Bug 分析头头是道，但指出的代码行根本没被调用 |
| **一致性幻觉** | 同一会话前后矛盾 | 第 3 条消息说用 React 18，第 8 条消息导入 React 16 的 API |
| **省略性幻觉** | 跳过关键步骤，声称完成 | 数据库迁移「完成」，但静默跳过了 14% 的记录 |

**抑制幻觉的 6 个方法**：

1. **Spec-Driven 开发**：提供精确的接口文档/类型定义，减少模型「脑补」空间
2. **Context7 MCP**：注入最新版本框架文档，防止模型用过时的 API
3. **约束性 Prompt**：明确要求「不确定的内容直接告知，禁止编造」
4. **Few-shot 示例**：给 2-3 个正确示例，校准输出格式
5. **自我验证**：要求 AI 写完代码后自己验证（跑测试/检查类型）
6. **Rule 规则约束**：在 CLAUDE.md 中写明「幻觉约束」规则（见第 2 周教程）

### 1.5 开源 vs 闭源模型选型

**码农选模型，核心看四个维度**：

| 维度 | 说明 |
|------|------|
| **代码能力** | 代码生成质量、Bug 修复准确率、跨文件理解能力 |
| **上下文窗口** | 能同时分析的代码量 |
| **成本** | API 价格（每百万 token） |
| **可用性** | 国内直连、数据合规、API 稳定性 |

#### 编程场景模型推荐

| 场景 | 推荐模型 | 理由 |
|------|---------|------|
| **复杂架构/大型重构** | Claude Opus 4 | 200K 上下文，代码质量 9.7/10 |
| **日常编码/快速迭代** | DeepSeek V3 / Claude Sonnet 4 | 性价比最优，质量不差 |
| **国内直连/免费** | DeepSeek V3 / Qwen 2.5 | 无需代理，中文理解 95%+ |
| **代码审查/Bug 定位** | Claude Opus 4 / GPT-5 | 逻辑推理最强 |
| **批量自动化** | OpenAI Codex（GPT-5 后端） | Token 效率约为 Claude Code 的 4 倍 |
| **本地私有化** | DeepSeek-Coder-7B / Qwen2.5-Coder-7B | 断网可用，零成本 |

#### Token 效率 ≠ 模型能力

一个容易被忽略的维度是 **Token 效率**。不同模型生成同等质量代码消耗的 token 量差异巨大：

| 模型 | Token 效率 | 说明 |
|------|-----------|------|
| OpenAI Codex（GPT-5 后端） | ⭐⭐⭐⭐⭐ | 约为 Claude Code 的 4 倍，适合批量任务 |
| Claude Opus 4 | ⭐⭐⭐⭐ | 单次质量最高，但 token 消耗较大 |
| DeepSeek V3 | ⭐⭐⭐ | 中文场景效率高，成本优势明显 |

> 💡 **实战策略**：Codex 做审查 + Debug（效率高），Claude Code 做架构 + 初始功能（推理深）。两者互补而非二选一。详见 [[Wiki/wiki/topics/ai-coding-tools-comparison|AI Coding 工具全景对比]]。

#### 实战产出：《程序员大模型选型手册》

完成本章学习后，你应该能产出一份类似下面的选型决策表：

```
我当前项目：Next.js 全栈应用，50+ 文件，主要用 TypeScript
主力模型：Claude Sonnet 4（200K 上下文覆盖全项目）
降本方案：DeepSeek V3（日常小改动用，成本低 80%）
本地兜底：Qwen2.5-Coder-7B（断网或 API 故障时切换）
效率补刀：Codex（批量重构 / 代码审查场景，token 效率 4 倍）
```

## 第二章：Prompt 工程核心

> 📖 本章对应学习计划 Day 3-4。

### 2.1 通用 Prompt 框架

#### CRISPE 框架

| 字母 | 含义 | 示例 |
|------|------|------|
| **C**apacity（能力） | 给 AI 设定角色和能力边界 | 「你是一个资深 TypeScript 开发者，精通 Next.js 和 Prisma」 |
| **R**ole（角色） | 具体身份 | 「作为项目架构师，帮我审查以下代码的架构合理性」 |
| **I**nsight（洞察） | 背景和上下文 | 「这个项目已经运行了 2 年，有 10 万行代码，核心痛点是……」 |
| **S**tatement（陈述） | 明确的任务 | 「重构 src/services/auth.ts，将 JWT 逻辑从 200 行拆分为 3 个模块」 |
| **P**ersonality（个性） | 输出风格 | 「代码优先，最少解释，不确定的地方直接标注 TODO」 |
| **E**xperiment（实验） | 迭代要求 | 「如果方案 1 有性能问题，给出方案 2（降级方案）」 |

#### ROLE 框架（精简版）

- **R**ole：角色定位
- **O**bjective：目标
- **L**imitations：限制条件
- **E**xpected output：期望输出格式

#### R-T-F 框架（最小可用版）

- **R**ole：角色
- **T**ask：任务
- **F**ormat：输出格式

> 💡 **实战建议**：日常编码用 R-T-F 最省 Token，复杂任务用 CRISPE 更精准。

### 2.2 Prompt 工程三板斧

详细的原理和代码实现见 [[Wiki/wiki/concepts/prompt-engineering-trilogy|Prompt 工程三板斧]]，这里给出程序员最实用的部分：

#### Few-shot：给 AI 看「标准答案」

Few-shot 的核心不是「给例子」——是**校准输出模式**。AI 会模仿你示例中的代码风格、命名规范、错误处理策略。

```markdown
## 示例 1
输入：为用户表添加 `last_login_at` 字段
输出：
```sql
ALTER TABLE users ADD COLUMN last_login_at TIMESTAMP;
CREATE INDEX idx_users_last_login ON users(last_login_at);
```

## 示例 2
输入：为订单表添加 `refund_status` 字段
输出：
```sql
ALTER TABLE orders ADD COLUMN refund_status VARCHAR(20) DEFAULT 'none';
CREATE INDEX idx_orders_refund_status ON orders(refund_status);
```

## 当前任务
输入：为商品表添加 `is_virtual` 字段
```

**静态 vs 动态 Few-shot**：

| 方式 | 做法 | 适用 |
|------|------|------|
| **静态 Few-shot** | 固定 2-3 个示例，写死在 Prompt 中 | 示例库小（< 20 条），任务模式固定 |
| **动态 Few-shot** | 按输入相似度自动选最相关的 k 个示例 | 示例库大，任务类型多样，需控制 token 预算 |

> ⚠️ **关键数据**：同一任务，零样本格式稳定性约 60%，三样本后 95%+。但**示例质量差，比不给示例更糟**——示例中有错误或格式不一致，会主动干扰模型输出。

#### CoT（Chain of Thought）：让 AI 写出推理过程

LLM 的前向传播是一次性的，中间状态不能回头修改。**强迫它把推理步骤写出来，相当于给每一步推理都分配了 token，而不是直接跳到答案。**

在多步推理任务（Bug 定位、性能分析、架构设计）上，CoT 可提升准确率 **15-25%**。

**两种 CoT 模式**：

| 模式 | 做法 | 适用 |
|------|------|------|
| **Zero-shot CoT** | 末尾加一句「请一步一步展示推理过程」 | 通用场景 |
| **Few-shot CoT** | 提供完整的「问题→推理步骤→答案」示例 | 格式敏感场景（代码生成、SQL） |

```markdown
任务：找出以下代码的性能瓶颈

要求：一步一步展示推理过程，最后一行以「结论：」开头给出最终判断
```

> ⚠️ **关键约束**：CoT 提示词**必须指定最后一行格式**（如「结论：」开头），否则模型写的步骤格式随意，导致后处理代码崩。

#### Self-Consistency：多路径投票

同一个问题，LLM 不同次运行可能给出不同答案（Temperature > 0 时尤其明显）。SC 的思路是：跑 N 次，投票选最多数的答案。

```
同一个需求 → 路径 1：[方案 A] 
           → 路径 2：[方案 A] → 投票 → 方案 A（3 票胜出）
           → 路径 3：[方案 A]
           → 路径 4：[方案 B]
           → 路径 5：[方案 A]
```

**参数建议**：
- N 至少设为**奇数**（3、5），避免平票
- Temperature 设 **0.5~0.8** 保证路径多样性
- 论文数据（Wei et al., 2022）：数学推理 +10-17%，常识推理 +13%

**是否值得用 SC**：

| 场景 | 是否值得 |
|------|---------|
| 精确数学/逻辑推理 | ✅ 值得 |
| 代码生成（多版本取最多数） | ✅ 值得 |
| 支付逻辑/安全校验/数据库迁移 | ✅ 必须 |
| 简单问答/信息检索 | ❌ 不值得 |
| 开放式创意写作 | ❌ 无意义 |
| 实时响应（<500ms） | ❌ 太慢 |

> 💡 成本提醒：SC 的 token 消耗是普通调用的 3-5 倍。**仅对关键代码使用**。

#### 三者组合：生产级方案

单独用这三个技术都很基础，组合起来才是生产级的用法：

| 策略 | 推理准确率 | 相对成本 | 延迟 | 适用场景 |
|------|-----------|---------|------|---------|
| Zero-shot | 基准 | 1x | 低 | 简单任务 |
| Few-shot | +10-15% | 1.2x | 低 | 格式敏感任务 |
| CoT | +15-25% | 1.3x | 中 | 多步推理 |
| Few-shot + CoT | +25-35% | 1.5x | 中 | 复杂推理 |
| Self-Consistency (N=5) | +35-50% | 5x | 高 | 高精度任务 |

#### 动态路由策略

不是所有问题都需要 CoT + SC。实战中用路由逻辑动态决定：

- **70% 简单问题**：直接 Zero-shot（省成本 80%）
- **30% 复杂问题**：Few-shot CoT + Self-Consistency（保准确率）

**总体效果**：相比全量上 SC，成本降低约 75%，平均延迟降低约 60%。

#### 三板斧的六个常见坑

| 坑 | 表现 | 解决方案 |
|----|------|---------|
| **Few-shot 示例质量差** | 输出格式反而变差 | 每次改 Prompt 先跑测试用例 |
| **CoT 未指定输出格式** | 后处理代码崩 | 明确最后一行格式（如「结论：」开头） |
| **SC 的 N 值设太小** | N=2 平票无法决出 | 至少奇数 3/5 |
| **工具调用 Agent 里用 CoT** | 工具参数提取变差 | 把推理放在独立字段，不要混在工具调用中 |
| **Prompt 改好了但不知道为什么** | 下次模型升级又崩 | Prompt 当代码管理（见 3.5 节） |
| **测试集太小** | 10 条调出来的在生产 10 万条上崩 | 至少 100+ 条覆盖边界 |

#### 三板斧与 Agent 的关系

这三板斧是 Agent 推理能力的基础支撑（详见 [[Wiki/wiki/concepts/ai-agent|AI Agent 概念页]]）：

- **Few-shot** → 校准 Agent 的工具调用格式
- **CoT** → 让 Agent 在「思考→行动→观察」循环中多步推理
- **Self-Consistency** → Agent 执行关键决策时多路径验证

在第 5 周学习 AI Agent 时，你会发现 Agent 的 ReAct 模式（Reasoning + Acting）本质上就是 CoT + 工具调用的结合。

### 2.3 代码专用 Prompt 模板（8 套）

以下是 8 套可直接复用的开发 Prompt 模板，覆盖日常编程 80% 的场景：

#### 模板 1：功能实现

```markdown
## 角色
你是资深 [语言/框架] 开发者。

## 任务
实现 [功能描述]。

## 约束
- 只输出代码，不要多余解释
- 所有代码必须可直接运行
- 不确定的地方用 TODO: 标注
- 附带最小注释（只解释「为什么」，不解释「做什么」）

## 上下文
- 技术栈：[列出]
- 相关文件：[列出路径]
- 现有模式：[描述代码库中的已有模式]
```

#### 模板 2：Bug 修复

```markdown
## 角色
你是专门负责定位和修复 Bug 的工程师。

## 问题
[描述 Bug 现象 + 复现步骤 + 期望行为]

## 推理要求
一步一步展示推理过程：
1. 阅读相关代码
2. 列出可能的根因（按可能性排序）
3. 逐一排除
4. 给出最小修复方案

## 约束

- 添加回归测试

```

### 2.4 结构化输出 Prompt

让 AI 输出结构化数据（JSON/YAML），而非自由文本——这对代码场景尤其重要。

```markdown
## 输出格式约束
请严格按以下 JSON 格式输出（不要包含其他内容）：

```json
{
  "analysis": "问题分析的摘要（一句话）",
  "rootCause": "根因定位",
  "fix": {
    "file": "修改的文件路径",
    "lineStart": 行号,
    "lineEnd": 行号,
    "before": "修改前的代码",
    "after": "修改后的代码"
  },
  "testSuggestion": "建议的测试用例"
}
```

如果无法确定某个字段的值，填 `null`，不要编造。
```

> ⚠️ **坑**：结构化输出的 Prompt 一定要加「不确定就填 null」的约束，否则 AI 会编造数据来满足 JSON 格式。

### 2.5 代码场景 Prompt 常见坑

以下 8 个坑是从真实编程场景中总结出来的，每个都可能让你的 Prompt 从「精准」变「翻车」：

| # | 坑 | 表现 | 解决方案 |
|---|-----|------|---------|
| 1 | **Prompt 描述过于模糊** | AI 自由发挥，代码风格不一致 | 用 R-T-F 框架明确角色/任务/格式 |
| 2 | **没有给出技术栈约束** | AI 用 React 16 的 API 写 React 18 项目 | Prompt 中明确「技术栈：React 18 + TypeScript 5.3」 |
| 3 | **依赖 AI 知道最新 API** | AI 用过时的 API/不存在的参数 | 注入 Context7 MCP 或粘贴最新文档片段 |
| 4 | **结构化输出不设 null 兜底** | AI 编造数据来满足 JSON 格式 | 加「不确定的字段填 null」约束 |
| 5 | **一次性给太大任务** | AI 中途遗忘约束，产出一半崩坏 | 拆分为多步，每步设检查点（见 3.2） |
| 6 | **给 AI 冲突的约束** | 「少写注释」和「解释每行逻辑」同时出现 | 检查 Prompt 中的矛盾指令 |
| 7 | **不看上下文就追加需求** | 上下文溢出，AI 遗忘最早的需求 | 用 `/compact` 压缩或新开会话 |
| 8 | **把 AI 当同事而非工具** | 「你懂的」「差不多那样」→ AI 真的会猜 | 像写代码一样写 Prompt：精确、可测试、无歧义 |

## 第三章：Prompt 实战进阶

> 📖 本章对应学习计划 Day 5-7。

### 3.1 Spec-Driven 开发模式

Spec-Driven 开发是程序员场景中最强大的 Prompt 范式：**先定义规格，再让 AI 按规格执行**。

```
传统：描述需求 → AI 自由发挥 → 逐行审查 → 修改 → 循环……
Spec-Driven：写规格文档（接口/类型/测试用例）→ AI 严格按规格实现 → 跑测试验证
```

#### 实战案例

**需求**：实现一个用户登录接口

**传统 Prompt**（❌ 不推荐）：
> 「帮我写一个登录接口」

**Spec-Driven Prompt**（✅ 推荐）：
> 「参照 `spec/auth.md` 中的接口定义，实现 `src/services/auth.ts` 的 `login` 函数。要求：严格按照 spec 中的请求/响应类型，密码用 bcrypt 验证，返回 JWT token，失败时返回 spec 中定义的错误码。」

**Spec-Driven 的核心优势**：
- AI 的自由发挥空间被精确约束
- 测试可以验证 AI 是否「按规格执行」
- 减少返工：规格写对了，实现就对了

### 3.2 需求拆解 Prompt

将一个模糊的大需求拆解为可执行的小任务：

```markdown
## 任务
将以下需求拆解为可独立开发的任务列表。

## 需求
[描述一个较模糊的需求]

## 拆解要求
- 每个任务 2-4 小时内可完成
- 标注任务之间的依赖关系
- 标注每个任务的优先级（P0/P1/P2）
- 标注不确定点（需与产品/后端确认的事项）
- 建议开发顺序

## 输出格式
| 序号 | 任务 | 预估工时 | 依赖 | 优先级 | 不确定点 |
```

### 3.3 Bug 修复 Prompt

```markdown
## 角色
你是 Bug 猎人。

## Bug 描述
- 现象：[用户看到什么 / 系统表现]
- 复现步骤：[精确步骤]
- 期望行为：[应该是什么样]
- 环境：[浏览器/Node 版本/操作系统]

## 工作流程
1. 先 grep 搜索相关代码（日志关键词、错误信息、涉及的函数名）
2. 阅读怀疑的代码区域
3. 提出 2-3 个可能的根因假设
4. 给出验证每个假设的方法（加日志/断点/单元测试）
5. 确定根因后，给出最小修复方案

## 约束
- 只输出可验证的结论，不猜测
- 如果信息不足，列出还需要的日志/数据
```

### 3.4 「零调试生成工业级代码」完整模板

这是第 1 周的终极实战产出——一个能生成可直接运行、符合团队规范代码的完整 Prompt 模板：

```markdown
# 工业级代码生成 Prompt

## 角色与能力
你是资深 [语言] 全栈工程师，已在当前项目工作 6 个月，熟悉所有代码规范和架构模式。

## 当前项目上下文
- 项目类型：[Web 应用 / API 服务 / CLI 工具 / 移动应用]
- 技术栈：[框架 + 语言 + 数据库 + 部署平台]
- 代码规范：见项目根目录 CLAUDE.md / .cursorrules
- 相关文件：[列出需要读取理解的文件路径]

## 任务
[一句话描述核心任务]

## 硬性约束（必须遵守）
1. **可运行性**：输出的代码必须能直接运行，所有依赖已在 package.json 中
2. **类型安全**：不使用 any/unknown，所有函数有明确类型签名
3. **错误处理**：每个外部调用（API/数据库/文件系统）有 try-catch 或 Result 类型
4. **注释原则**：只解释「为什么」（设计决策），不解释「做什么」（代码自解释）
5. **最少修改**：只改实现目标必需的代码，不重构无关代码
6. **现有模式**：严格遵循代码库已有的设计模式和命名惯例
7. **不确定性**：不确定的 API/参数/行为直接标注 TODO: verify，禁止编造

## 输出要求
1. **先读**：在写代码前，先列出你阅读了哪些文件、理解了哪些模式
2. **计划**：给出修改计划（涉及文件、修改范围、风险点）
3. **实现**：按计划逐步修改
4. **验证**：确认所有修改一致（import 是否正确、类型是否匹配、调用方是否需更新）

## 成功标准
- [ ] 代码能通过 TypeScript 类型检查
- [ ] 所有现有测试通过
- [ ] 新增功能有覆盖测试
- [ ] 代码审查可接受（可维护、可读、一致）
```

### 3.5 Prompt 版本管理与测试

> 💡 **核心理念**：把 Prompt 当代码管理——有版本、有测试、有回滚。否则下次模型升级，你的 Prompt 可能静默崩坏。

#### 为什么需要版本管理

LLM 模型会持续迭代（Claude 3.5 → 4 → Opus 4），API 行为会变化。一个在 Claude Opus 3 上调好的 Prompt，在 Opus 4 上可能输出完全不同的结果。没有版本管理的 Prompt：

- 改好了不知道为什么好
- 改坏了无法回滚到上一个可用版本
- 不同项目用同一套 Prompt 时不知道哪个版本适配哪个模型

#### Prompt 版本管理实操

```markdown
# Prompt 仓库结构
prompts/
├── code-generation/
│   ├── v1.0.0-basic.md          # 基础版：R-T-F 框架
│   ├── v1.1.0-with-constraints.md # 增强版：加了硬性约束
│   ├── v2.0.0-spec-driven.md    # Spec-Driven 版
│   └── CHANGELOG.md             # 变更记录
├── bug-fix/
│   ├── v1.0.0-cot.md
│   └── v2.0.0-cot-sc.md         # 加了 Self-Consistency
└── tests/
    ├── code-gen-cases.json       # 测试用例
    └── evaluate.sh               # 自动化评估脚本
```

**CHANGELOG.md 示例**：

```markdown
## v2.0.0 (2026-06-01)
- 新增 Spec-Driven 约束层
- 移除过于宽泛的「写出好代码」约束（效果不可验证）
- 新增成功标准 checklist
- 测试数据：TypeScript 类型检查通过率 97% → 100%
- 适用模型：Claude Opus 4 / Sonnet 4

## v1.1.0 (2026-05-15)
- 新增「不确定就标注 TODO: verify」约束
- 幻觉率从 8% 降至 2%
```

#### Prompt 测试策略

**最少需要 3 类测试用例**：

| 测试类型 | 说明 | 数量建议 |
|---------|------|---------|
| **黄金用例** | 验证核心功能是否正常 | 5-10 条 |
| **边界用例** | 极端输入、空值、超长文本 | 5-10 条 |
| **回归用例** | 之前修过的 Bug，确保不再复现 | 持续积累 |

**测试流程**：

```
1. 准备 10+ 条测试用例（输入 + 期望输出）
2. 用当前 Prompt 跑一遍，记录输出
3. 修改 Prompt 后，再跑一遍
4. 对比两轮结果：
   - 改进了哪些用例？
   - 有没有原本能过的用例现在崩了？（回归）
5. 只有改进 ≥ 0 且回归 = 0，才算成功迭代
```

> ⚠️ **血泪教训**：10 条测试用例调出来的 Prompt，在生产 10 万条上可能崩。至少积累 100+ 条覆盖边界。
