## 第一章：LLM 底层认知

> 📖 本章对应学习计划 Day 1-2。

### 1.1 什么是大语言模型（LLM）

大语言模型的核心能力是**预测下一个 token**。给定一段文本，模型计算每个可能的下一个词的概率，选择最可能的那一个——然后把这个词加到输入中，继续预测下一个。

这个简单的机制，在超大规模（数千亿参数）和海量语料（万亿级 token）训练后，涌现出了推理、翻译、编程等复杂能力。

**关键认知**：LLM 不是数据库，不是搜索引擎，不是推理引擎。它是一个**概率性的文本补全系统**——理解这一点，才能理解它为什么会产生幻觉、为什么需要 Prompt 工程。

### 1.2 Transformer 极简原理

不需要数学推导，只需理解三个核心概念：

| 概念 | 一句话解释 | 对编程的影响 |
|------|-----------|------------|
| **自注意力（Self-Attention）** | 每个词「看到」句子中所有其他词，计算关联强度 | 模型能理解长距离依赖（如函数调用关系） |
| **多层堆叠** | 注意力层反复叠加（几十到上百层） | 浅层学语法，深层学语义，最深层学推理 |
| **位置编码** | 给每个 token 标位置（第 1 个、第 2 个……） | 代码顺序至关重要——模型对代码位置敏感 |

> 📖 如需深入理解，推荐阅读 Jay Alammar 的《The Illustrated Transformer》（图文并茂，无数学公式）。

### 1.3 上下文窗口与 Token 机制

**Token 是什么**：LLM 处理的不是「字」，而是 token——文本被切分后的最小处理单元。

```
中文：1 个汉字 ≈ 1.5-2 个 token
英文：1 个单词 ≈ 1.3 个 token
代码：因语言而异，Python 约 1 个词 ≈ 1 token
```

**上下文窗口**：模型一次能「看到」的最大 token 数量。超过窗口的内容会被遗忘。

| 模型 | 上下文窗口 | 代码场景建议 |
|------|-----------|------------|
| Claude Opus 4 | 200K token | 完整项目级分析 |
| GPT-5 | 128K token | 多文件开发 |
| DeepSeek V3 | 128K token | 性价比之选 |
| Qwen 2.5 | 128K token | 国内替代方案 |
| Gemini 2.5 Pro | 1M token | 超大代码库分析 |

**Token 消耗的实战经验**：
- 一次完整的 Claude Code 会话通常消耗 10K-50K token
- 复杂多文件重构可能消耗 100K+ token
- `/compact` 命令可以压缩上下文，保留关键信息，节省约 40-60% token

### 1.4 模型幻觉：成因、识别与抑制

**幻觉（Hallucination）** 是 LLM 最核心的缺陷之一。模型**不是故意撒谎**——它只是在做概率补全时，「猜」出了一个看起来合理但事实上错误的内容。

**四种幻觉类型**：

| 类型 | 表现 | 例子 |
|------|------|------|
| **事实性幻觉** | 编造不存在的 API/参数/文档 | 调用 `fs.rmSync(dir, {force: true})`——实际没有 `force` 选项 |
| **逻辑性幻觉** | 推理过程看似合理，结论错误 | Bug 分析头头是道，但指出的代码行根本没被调用 |
| **一致性幻觉** | 同一会话前后矛盾 | 第 3 条消息说用 React 18，第 8 条消息导入 React 16 的 API |
| **省略性幻觉** | 跳过关键步骤，声称完成 | 数据库迁移「完成」，但静默跳过了 14% 的记录 |

**抑制幻觉的 6 个方法**：

1. **Spec-Driven 开发**：提供精确的接口文档/类型定义，减少模型「脑补」空间
2. **Context7 MCP**：注入最新版本框架文档，防止模型用过时的 API
3. **约束性 Prompt**：明确要求「不确定的内容直接告知，禁止编造」
4. **Few-shot 示例**：给 2-3 个正确示例，校准输出格式
5. **自我验证**：要求 AI 写完代码后自己验证（跑测试/检查类型）
6. **Rule 规则约束**：在 CLAUDE.md 中写明「幻觉约束」规则（见第 2 周教程）

### 1.5 开源 vs 闭源模型选型

**码农选模型，核心看四个维度**：

| 维度 | 说明 |
|------|------|
| **代码能力** | 代码生成质量、Bug 修复准确率、跨文件理解能力 |
| **上下文窗口** | 能同时分析的代码量 |
| **成本** | API 价格（每百万 token） |
| **可用性** | 国内直连、数据合规、API 稳定性 |

#### 编程场景模型推荐

| 场景 | 推荐模型 | 理由 |
|------|---------|------|
| **复杂架构/大型重构** | Claude Opus 4 | 200K 上下文，代码质量 9.7/10 |
| **日常编码/快速迭代** | DeepSeek V3 / Claude Sonnet 4 | 性价比最优，质量不差 |
| **国内直连/免费** | DeepSeek V3 / Qwen 2.5 | 无需代理，中文理解 95%+ |
| **代码审查/Bug 定位** | Claude Opus 4 / GPT-5 | 逻辑推理最强 |
| **批量自动化** | OpenAI Codex（GPT-5 后端） | Token 效率约为 Claude Code 的 4 倍 |
| **本地私有化** | DeepSeek-Coder-7B / Qwen2.5-Coder-7B | 断网可用，零成本 |

#### 实战产出：《程序员大模型选型手册》

完成本章学习后，你应该能产出一份类似下面的选型决策表：

```
我当前项目：Next.js 全栈应用，50+ 文件，主要用 TypeScript
主力模型：Claude Sonnet 4（200K 上下文覆盖全项目）
降本方案：DeepSeek V3（日常小改动用，成本低 80%）
本地兜底：Qwen2.5-Coder-7B（断网或 API 故障时切换）
```

### 2.1 通用 Prompt 框架

#### CRISPE 框架

| 字母 | 含义 | 示例 |
|------|------|------|
| **C**apacity（能力） | 给 AI 设定角色和能力边界 | 「你是一个资深 TypeScript 开发者，精通 Next.js 和 Prisma」 |
| **R**ole（角色） | 具体身份 | 「作为项目架构师，帮我审查以下代码的架构合理性」 |
| **I**nsight（洞察） | 背景和上下文 | 「这个项目已经运行了 2 年，有 10 万行代码，核心痛点是……」 |
| **S**tatement（陈述） | 明确的任务 | 「重构 src/services/auth.ts，将 JWT 逻辑从 200 行拆分为 3 个模块」 |
| **P**ersonality（个性） | 输出风格 | 「代码优先，最少解释，不确定的地方直接标注 TODO」 |
| **E**xperiment（实验） | 迭代要求 | 「如果方案 1 有性能问题，给出方案 2（降级方案）」 |

#### ROLE 框架（精简版）

- **R**ole：角色定位
- **O**bjective：目标
- **L**imitations：限制条件
- **E**xpected output：期望输出格式

#### R-T-F 框架（最小可用版）

- **R**ole：角色
- **T**ask：任务
- **F**ormat：输出格式

> 💡 **实战建议**：日常编码用 R-T-F 最省 Token，复杂任务用 CRISPE 更精准。

### 2.2 Prompt 工程三板斧

详细的原理和代码实现见 [[Wiki/wiki/concepts/prompt-engineering-trilogy|Prompt 工程三板斧]]，这里给出程序员最实用的部分：

#### Few-shot：给 AI 看「标准答案」

```markdown
## 示例 1
输入：为用户表添加 `last_login_at` 字段
输出：
```sql
ALTER TABLE users ADD COLUMN last_login_at TIMESTAMP;
CREATE INDEX idx_users_last_login ON users(last_login_at);
```

## 示例 2
输入：为订单表添加 `refund_status` 字段
输出：
```sql
ALTER TABLE orders ADD COLUMN refund_status VARCHAR(20) DEFAULT 'none';
CREATE INDEX idx_orders_refund_status ON orders(refund_status);
```

## 当前任务
输入：为商品表添加 `is_virtual` 字段
```

Few-shot 的核心不是「给例子」——是**校准输出模式**。AI 会模仿你示例中的 SQL 风格、命名规范、索引策略。

#### CoT（Chain of Thought）：让 AI 写出推理过程

```markdown
任务：找出以下代码的性能瓶颈

要求：一步一步展示推理过程，最后一行以「结论：」开头给出最终判断
```

在多步推理任务（Bug 定位、性能分析、架构设计）上，CoT 可提升准确率 **15-25%**。

#### Self-Consistency：多路径投票

对关键代码（支付逻辑、安全校验、数据库迁移），让 AI 生成 3-5 次，选结果最多的一致方案。

```
同一个需求 → 路径 1：[方案 A] 
           → 路径 2：[方案 A] → 投票 → 方案 A（3 票胜出）
           → 路径 3：[方案 A]
           → 路径 4：[方案 B]
           → 路径 5：[方案 A]
```

> 💡 成本提醒：SC 的 token 消耗是普通调用的 3-5 倍。**仅对关键代码使用**。

### 2.3 代码专用 Prompt 模板（8 套）

以下是 8 套可直接复用的开发 Prompt 模板，覆盖日常编程 80% 的场景：

#### 模板 1：功能实现

```markdown
## 角色
你是资深 [语言/框架] 开发者。

## 任务
实现 [功能描述]。

## 约束
- 只输出代码，不要多余解释
- 所有代码必须可直接运行
- 不确定的地方用 TODO: 标注
- 附带最小注释（只解释「为什么」，不解释「做什么」）

## 上下文
- 技术栈：[列出]
- 相关文件：[列出路径]
- 现有模式：[描述代码库中的已有模式]
```

#### 模板 2：Bug 修复

```markdown
## 角色
你是专门负责定位和修复 Bug 的工程师。

## 问题
[描述 Bug 现象 + 复现步骤 + 期望行为]

## 推理要求
一步一步展示推理过程：
1. 阅读相关代码
2. 列出可能的根因（按可能性排序）
3. 逐一排除
4. 给出最小修复方案

## 约束
- 只修改导致 Bug 的代码，不碰其他逻辑
- 添加回归测试
- 解释为什么修复是安全的
```

#### 模板 3：代码审查

```markdown
## 角色
你是高级代码审查员。

## 审查内容
[代码块或文件路径]

## 审查维度（5 维度打分）
1. 正确性：逻辑是否正确？边界情况是否覆盖？
2. 安全性：有无注入/越权/数据泄露风险？
3. 性能：有无 N+1 查询、不必要的循环、内存泄漏？
4. 可维护性：命名是否清晰？函数是否过长？是否有重复代码？
5. 一致性：是否遵循代码库现有模式？

## 输出格式
每个维度：得分（1-10）+ 具体问题 + 改进建议
```

#### 模板 4：代码重构

```markdown
## 角色
你是代码重构专家。

## 重构目标
[文件/模块路径]：当前 [X 行]，目标拆分为 [Y 个模块]

## 约束
- 保持所有现有测试通过
- 不改变外部 API（调用方零修改）
- 保持现有命名风格
- 每步重构后运行测试

## 计划要求
先给出重构计划（分步、每步影响范围、风险），确认后再执行。
```

#### 模板 5：SQL 生成

```markdown
## 角色
你是数据库专家，精通 SQL 优化。

## 需求
[自然语言描述查询需求]

## 约束
- 使用 [PostgreSQL/MySQL] 语法
- 表结构来自 [prisma schema 路径]
- 考虑已有索引
- 标注可能慢查询的部分
- 附带 EXPLAIN 分析建议
```

#### 模板 6：单元测试生成

```markdown
## 角色
你是测试工程师。

## 测试目标
[文件/函数路径]

## 要求
- 测试框架：[Vitest / Jest / pytest]
- 覆盖：正常路径 + 边界值 + 异常情况 + 空值/null
- 每个测试要有清晰的 describe/it 描述
- Mock 外部依赖（数据库/API）
- 测试意图注释（为什么这个测试重要）

## 约束
不修改被测代码。
```

#### 模板 7：API 接口设计

```markdown
## 角色
你是后端架构师，擅长 RESTful API 设计。

## 需求
[功能描述]

## 输出格式
每个接口输出以下内容：
- 方法 + 路径
- 请求参数（类型 + 必填 + 说明）
- 响应体（成功 + 错误格式）
- 业务逻辑要点
- 错误处理策略
```

#### 模板 8：技术方案设计

```markdown
## 角色
你是全栈架构师。

## 问题
[描述业务问题和技术约束]

## 要求
给出 2-3 个备选方案，每个方案包含：
1. 核心思路（2-3 句话）
2. 优势（3 个要点）
3. 风险（3 个要点）
4. 技术选型建议
5. 预估开发工时

## 约束
- 优先使用现有技术栈
- 考虑团队经验和维护成本
- 标注需要验证的假设
```

### 2.4 结构化输出 Prompt

让 AI 输出结构化数据（JSON/YAML），而非自由文本——这对代码场景尤其重要。

```markdown
## 输出格式约束
请严格按以下 JSON 格式输出（不要包含其他内容）：

```json
{
  "analysis": "问题分析的摘要（一句话）",
  "rootCause": "根因定位",
  "fix": {
    "file": "修改的文件路径",
    "lineStart": 行号,
    "lineEnd": 行号,
    "before": "修改前的代码",
    "after": "修改后的代码"
  },
  "testSuggestion": "建议的测试用例"
}
```

如果无法确定某个字段的值，填 `null`，不要编造。
```

> ⚠️ **坑**：结构化输出的 Prompt 一定要加「不确定就填 null」的约束，否则 AI 会编造数据来满足 JSON 格式。

## 第三章：Prompt 实战进阶

> 📖 本章对应学习计划 Day 5-7。

### 3.1 Spec-Driven 开发模式

Spec-Driven 开发是程序员场景中最强大的 Prompt 范式：**先定义规格，再让 AI 按规格执行**。

```
传统：描述需求 → AI 自由发挥 → 逐行审查 → 修改 → 循环……
Spec-Driven：写规格文档（接口/类型/测试用例）→ AI 严格按规格实现 → 跑测试验证
```

#### 实战案例

**需求**：实现一个用户登录接口

**传统 Prompt**（❌ 不推荐）：
> 「帮我写一个登录接口」

**Spec-Driven Prompt**（✅ 推荐）：
> 「参照 `spec/auth.md` 中的接口定义，实现 `src/services/auth.ts` 的 `login` 函数。要求：严格按照 spec 中的请求/响应类型，密码用 bcrypt 验证，返回 JWT token，失败时返回 spec 中定义的错误码。」

**Spec-Driven 的核心优势**：
- AI 的自由发挥空间被精确约束
- 测试可以验证 AI 是否「按规格执行」
- 减少返工：规格写对了，实现就对了

### 3.2 需求拆解 Prompt

将一个模糊的大需求拆解为可执行的小任务：

```markdown
## 任务
将以下需求拆解为可独立开发的任务列表。

## 需求
[描述一个较模糊的需求]

## 拆解要求
- 每个任务 2-4 小时内可完成
- 标注任务之间的依赖关系
- 标注每个任务的优先级（P0/P1/P2）
- 标注不确定点（需与产品/后端确认的事项）
- 建议开发顺序

## 输出格式
| 序号 | 任务 | 预估工时 | 依赖 | 优先级 | 不确定点 |
```

### 3.3 Bug 修复 Prompt

```markdown
## 角色
你是 Bug 猎人。

## Bug 描述
- 现象：[用户看到什么 / 系统表现]
- 复现步骤：[精确步骤]
- 期望行为：[应该是什么样]
- 环境：[浏览器/Node 版本/操作系统]

## 工作流程
1. 先 grep 搜索相关代码（日志关键词、错误信息、涉及的函数名）
2. 阅读怀疑的代码区域
3. 提出 2-3 个可能的根因假设
4. 给出验证每个假设的方法（加日志/断点/单元测试）
5. 确定根因后，给出最小修复方案

## 约束
- 只输出可验证的结论，不猜测
- 如果信息不足，列出还需要的日志/数据
```

### 3.4 「零调试生成工业级代码」完整模板

这是第 1 周的终极实战产出——一个能生成可直接运行、符合团队规范代码的完整 Prompt 模板：

```markdown
# 工业级代码生成 Prompt

## 角色与能力
