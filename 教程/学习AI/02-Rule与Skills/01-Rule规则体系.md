> 📖 对应学习计划 Day 1-3。深度解析见 [[Wiki/wiki/topics/claude-md-12-rules|CLAUDE.md 12 条规则深度解析]]。

## 1.1 Rule 的本质：行为契约

Rule 不是「愿望清单」——它是一份**行为契约**。每一条 Rule 必须对应你观察到的**具体失败模式**。

**Rule 的核心价值**：
- **消除重复沟通**：不用每次新会话都解释技术栈、规范、偏好
- **约束 AI 行为**：告诉 AI「在这个项目里边界在哪」
- **减少失误率**：有实验数据显示，好的 Rule 可将失误率从 41% 降至 3%

> ⚠️ **关键原则**：Rule 不是越多越好。CLAUDE.md 超过 200 行后，合规率断崖下降。AI 会「遗忘」被噪声淹没的重要规则。

### Rule 的失败驱动设计法

每条 Rule 都应该来自你实际踩过的坑：

```
1. 观察 → AI 做了什么让你不爽的事？
2. 诊断 → 根本原因是什么？（自由发挥？缺少上下文？）
3. 约束 → 用一句话堵住这个行为模式
4. 验证 → 下次遇到类似场景，AI 是否遵守？
```

**反面案例**（❌ 愿望清单式 Rule）：
```markdown
# 不好的 Rule
- 写出高质量的代码
- 保持代码整洁
- 遵循最佳实践
```
这些"Rule"太空泛，AI 无法执行——它不知道你眼中的"高质量"是什么标准。

**正面案例**（✅ 行为契约式 Rule）：
```markdown
# 好的 Rule
- 不确定就问，不要猜
- 只改实现目标必需的代码，不重构无关代码
- 所有外部调用必须有 try-catch
```

## 1.2 各工具的 Rule 体系

| 工具 | Rule 文件 | 作用域 | 加载方式 |
|------|----------|--------|---------|
| **Claude Code** | `CLAUDE.md` | 项目根目录 / 用户级 `~/.claude/` | 每次会话自动加载 |
| **Cursor** | `.cursorrules` | 项目根目录 | 每次会话自动加载 |
| **Trae** | `.trae/rules.md` | 项目根目录 | 每次会话自动加载 |
| **Codex** | `AGENTS.md` | 项目根目录 | 每次会话自动加载 |
| **Hermes Agent** | `AGENTS.md` + `SOUL.md` | 项目级（规矩）+ 用户级（性格） | 每次会话自动加载 |

### CLAUDE.md 层级结构

Claude Code 的 Rule 有三层（按优先级从高到低）：

```
1. 会话级指令（本次对话中直接告诉 Claude 的）
     ↓ 覆盖
2. 项目级 CLAUDE.md（项目根目录）
     ↓ 覆盖
3. 用户级 CLAUDE.md（~/.claude/CLAUDE.md）
```

**实际加载顺序**：先加载企业共享的 CLAUDE.md → 追加用户级 CLAUDE.md → 追加项目级 CLAUDE.md → 最终以项目级为准（层级越高优先级越高）。

### 各工具 Rule 文件适配对照表

| 规则内容 | Claude Code `CLAUDE.md` | Cursor `.cursorrules` | Trae `.trae/rules.md` |
|---------|------------------------|----------------------|----------------------|
| 身份定位 | `你是资深软件开发工程师` | 同左 | 同左 |

| 格式约束 | `代码块标注语言类型` | 同左 | 同左 |

## 1.3 Karpathy 4 条基础规则

这 4 条规则是 Andrej Karpathy 2026 年 1 月提出的，堵住了约 **40%** 的无监督 Claude Code 翻车：

| 规则 | 核心要求 | 防止的失败模式 |
|------|---------|-------------|
| **1. 先想再写** | 明确说出假设，不确定就问，有更简单方案就 push back | 静默做错假设 |
| **2. 简单第一** | 最少代码解决问题，不写推测性功能，不建不必要的抽象 | 过度设计 |
| **3. 精准改动** | 只碰必须改的，不改相邻代码和注释，匹配现有风格 | 附带破坏 |
| **4. 目标驱动执行** | 定义成功标准，循环迭代直到验证通过 | 弱成功标准（过早停止或无限循环） |

### 每条规则的深度解读

**规则 1：先想再写（Think before you write）**

这条规则要求 AI 在动手之前先「说出它的假设」。为什么重要？AI 经常在理解偏差的情况下自信地写出代码。

```markdown
# 在 CLAUDE.md 中这样写：
## 规则 1：先想再写
- 在修改代码前，先列出你理解的需求和关键假设
- 如果需求有 2 种以上理解方式，先确认再动手
- 如果发现更简单的实现方案，主动提出
- 不确定的 API/参数直接标注 TODO: verify
```

**规则 2：简单第一（Simplicity first）**

AI 的最大问题不是不会写代码，而是写得太多。它会为"可能的未来需求"添加抽象层，为你不需要的功能写完整实现。

```markdown
# 在 CLAUDE.md 中这样写：
## 规则 2：简单第一
- 用最少代码解决问题
- 不写推测性功能（用户没要求的别加）
- 不建不必要的抽象层（除非有 3+ 个调用者）
- 如果你自己的方案让你觉得复杂，那就是复杂了
```

**规则 3：精准改动（Precise changes）**

AI 经常会顺手重构相邻代码、修改不相关的注释、或把代码改成自己喜欢的风格。

```markdown
# 在 CLAUDE.md 中这样写：
## 规则 3：精准改动
- 只改实现目标必需的代码
- 不改相邻的函数/变量/注释/格式
- 严格匹配项目现有的代码风格
- 如果项目用 class component，不要引入 hooks
```

**规则 4：目标驱动执行（Goal-driven execution）**

AI 容易陷入两个极端：过早宣布"完成"（实际还有问题），或无限循环优化。

```markdown
# 在 CLAUDE.md 中这样写：
## 规则 4：目标驱动执行
- 每个任务开始前，定义明确的成功标准
- 完成实现后，自检：代码能通过类型检查吗？所有现有测试通过吗？
- 如果有验证失败的项，继续修复直到全部通过
- 如果 3 次迭代后仍无法解决，停止并报告卡点
```

## 1.4 辰北 8 条增量规则（2026 年 5 月）

这 8 条规则覆盖了 Karpathy 原版没触及的新失败模式——Agent 缠斗、Hook 级联、跨 Session 工作流：

| 规则 | 一句话 | 翻车现场 |
|------|-------|---------|
| **5. 别让模型做代码就能干的事** | 确定性逻辑交给代码，判断力任务交给模型 | 用 Claude 决策 503 重试——重试策略变成随机 |
| **6. Token 预算是硬约束** | 每任务 4000 token，超了总结重启 | 一次调试跑 90 分钟，模型忘了试过哪些方案 |
| **7. 暴露冲突，别取平均** | 两套模式冲突时选一套，不写「平均」代码 | Claude 写的代码同时用了两种错误处理模式 |
| **8. 先读再写** | 加代码前先读文件的 exports、调用者、共享工具 | 在已有相同函数的代码旁又加了一模一样的函数 |
| **9. 测试验证意图** | 测试必须编码 WHY，不是 WHAT | 12 个测试全过，生产挂了——测的是「有返回值」不是「返回值正确」 |
| **10. 长流程设检查点** | 每步完成总结做了什么、验证了什么、还剩什么 | 6 步重构第 4 步翻车，已把 5、6 步也做完了 |
| **11. 惯例优先于品味** | 代码库内的遵守 > 个人品味 | class-component 项目里引入 React hooks，测试全崩 |
| **12. 失败要喊出来** | 跳过/静默失败 ≠ 完成，默认暴露不确定性 | 迁移脚本静默跳过 14% 记录，11 天后才发现 |

### 重点规则深度解析

**规则 5：别让模型做代码就能干的事（Don't use model for what code can do）**

这条规则之所以排在辰北增量规则第一条，是因为它堵住了一个隐蔽的失败模式：**把需要确定性的决策交给概率系统**。

```
❌ 错误：让 AI 决策重试策略
  → AI 有时等 1 秒重试，有时等 5 秒，有时不等
  → 重试行为变得不可预测

✅ 正确：代码写死重试逻辑（指数退避），AI 只负责判断"是否值得重试"
  → 重试间隔确定、可预测、可监控
```

**规则 6：Token 预算是硬约束（Token budget is a hard constraint）**

这是应对 Agent 模式特有的失败模式：**长任务中模型遗忘早期决策**。

```markdown
# 在 CLAUDE.md 中这样写：
## 规则 6：Token 预算是硬约束
- 每个独立任务的目标 Token 消耗 ≤ 4000
- 如果任务可能超预算，拆分为子任务
- 每完成一个子任务，输出简短总结（做了什么、验证了什么、还剩什么）
- 如果当前会话 Token 已超预算的 80%，停止并总结进展
```

**规则 12：失败要喊出来（Fail loudly）**

这是 12 条规则中**最重要也最容易被忽略的一条**。AI 倾向于「平滑处理」错误——跳过、静默失败、或用近似值代替。

```markdown
# 在 CLAUDE.md 中这样写：
## 规则 12：失败要喊出来
- 遇到任何错误/异常/不确定情况 → 立即报告，不要静默处理
- 不要用 try-catch 吞掉错误后继续执行
- 数据迁移/转换中如果有些记录处理失败 → 明确报告数量和原因
- 「跳过」≠「完成」
```

## 1.5 程序员通用全局 Rule 模板

以下是直接可用于所有 AI 调用（Claude Code / Cursor / Trae / Codex）的通用 Rule 模板：

```markdown
# 全局 AI 调用强制规则

## 1. 身份定位
你是资深软件开发工程师。输出内容贴合工业级开发标准。

## 2. 代码优先原则
- 直接给代码，少解释——除非我明确要求解释
- 代码必须可直接运行，标注运行环境和依赖版本
- 不确定的 API/参数直接标注 TODO: verify，禁止编造

## 3. 最少修改原则
- 只改实现当前目标必需的代码
- 不重构无关代码、不改相邻注释和格式
- 匹配现有代码风格（命名、缩进、模式）

## 4. 不确定性原则
- 不确定就问，不要猜
- 需要更多上下文才能判断时，列出你还需要什么信息
- 如果有 2 个以上可行方案，列出各方案的 trade-off

## 5. 简单优先原则
- 用最少代码解决问题
- 不为「可能的未来需求」写抽象层
- 如果方案让你自己都觉得复杂，那就是复杂了

## 6. 工具使用约束
- 单次调用不超过 3 个工具
- 复杂任务自动拆分为多步，每步设检查点
- 远程操作（git push / 数据库写入）执行前二次确认

## 7. 格式约束
- 代码块标注语言类型
- Markdown 格式输出
- 文件路径使用相对路径
```

### 将模板部署到各工具

```bash
# Claude Code：全局 Rule
cp global-rule.md ~/.claude/CLAUDE.md

# Claude Code：项目级 Rule（覆盖全局）
cp global-rule.md ./CLAUDE.md
# 然后根据项目特点修改 ./CLAUDE.md

# Cursor
cp global-rule.md ./.cursorrules

# Trae
mkdir -p .trae && cp global-rule.md ./.trae/rules.md

# Codex / Hermes
cp global-rule.md ./AGENTS.md
```

## 1.6 按阶段定制 Rule 严格度

不同开发阶段需要不同的 Rule 强度：

| 阶段 | Rule 强度 | 特殊规则 |
|------|---------|---------|
| **原型探索** | 宽松 | 显式声明 `## Override: Rule 2 (Simplicity) suspended for prototyping` |
| **功能开发** | 标准 | 套用完整规则 |
| **Bug 修复** | 严格 | 额外规则：「只输出根因分析和最小修复，不输出探索性代码」 |
| **代码审查** | 严格 | 额外规则：「不做任何修改，只输出审查意见」 |
| **生产部署** | 最严格 | 额外规则：「所有命令执行前二次确认，禁止自动执行破坏性操作」 |

### 阶段切换的实操方式

```markdown
# 在 CLAUDE.md 顶部加一行：
## 当前阶段：原型探索
## Override: Rule 2 (Simplicity) suspended for prototyping
## Override: Rule 6 (Token Budget) increased to 8000

# 进入功能开发后改为：
## 当前阶段：功能开发
## All rules in effect
```

## 1.7 编写 CLAUDE.md 的 5 步实操

```
1. 克隆通用模板 → 复制 1.5 节的通用 Rule 模板
2. 注入项目信息 → 技术栈、目录结构、构建命令、环境变量
3. 添加团队规范 → 命名约定、Git 规范、代码审查标准
4. 补充已知坑 → 项目中已知的 tricky 部分（「这个地方容易出错，注意 xxx」）
5. 验证并精简 → 跑 3-5 个真实任务，看 AI 是否遵守，精简不奏效的规则
```

**项目信息注入模板**：

```markdown
## 项目上下文
- 项目类型：Web 应用
- 技术栈：Next.js 14 + TypeScript + Prisma + PostgreSQL
- 包管理器：pnpm
- Node 版本：20 LTS
- 构建命令：pnpm build
- 测试命令：pnpm test
- 数据库：pnpm prisma migrate dev
```
