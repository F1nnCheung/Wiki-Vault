# 生产级 RAG 架构设计

> 以 Kubernetes 全套文档为示例知识库，从零构建一个完整的生产级 RAG 系统。核心决策：Qdrant 混合搜索（70% Embedding + 30% BM25）、六步摄取管线、相邻 Chunk 扩展 + Reranker 重排序、开源自托管与云服务的混合部署策略。

## 高层架构

RAG 由两个独立流程组成：

```
┌─────────────────────────────────────────────────────┐
│                    数据摄取管线                        │
│  提取 → 预处理 → 切分 → 元数据 → 向量化 → 存储        │
└─────────────────────────────────────────────────────┘
                         ↓
┌─────────────────────────────────────────────────────┐
│                  检索 + 生成                          │
│  用户查询 → 向量化 → 混合搜索 → 扩展相邻Chunk          │
│  → Reranker重排序 → LLM 生成回答                      │
└─────────────────────────────────────────────────────┘
```

**最重要的决策依据**：你的数据是什么格式？是否高度结构化？有没有元数据需索引？规模多大？用户怎么搜索？

## 搜索方式选择：混合搜索

### 关键词搜索（稀疏向量 / BM25）

从查询中提取单词，与文档库中单词匹配。BM25 通过逆文档频率（IDF）为 token 分配权重——降低高频词的噪声。

**优势**：精确匹配特定术语、代码、配置项。
**局限**：查询中的词在知识库中不存在时会失效。

### Embedding 语义搜索（稠密向量）

将文本转为数值向量，语义相近的词在向量空间中位置接近。使用余弦相似度查找语义匹配。

**优势**：理解语义，不依赖精确词汇匹配。
**局限**：可能召回「语义相似但答案不相关」的内容。

### 混合搜索 = 两者组合

**推荐权重**：70% Embedding + 30% BM25（RRF 融合）

Embedding 贡献大部分检索质量，BM25 帮助搜索特定术语。这是生产环境最常见的比例。

### 数据库选型：Qdrant

| 因素 | Qdrant 表现 |
|------|------------|
| 混合搜索 | 原生支持 Dense + Sparse Vectors + RRF |
| 开源 | 是，Docker 部署简单 |
| 性能 | Rust 编写，高性能低延迟 |
| 生态 | .NET/Python/Node SDK 完善 |

其他支持混合搜索的数据库：Weaviate、Pinecone、Milvus。

## 数据摄取管线（六步）

### 第一步：提取（Extraction）

从源文档提取文本和元数据（名称、页码、摘要）。如果文档有章节结构，**按章节提取**——确保后续 Chunk 不跨越章节边界。

三种提取策略：
- **SimplePdfExtractor**：提取全部文本为单章节
- **BookmarkPdfExtractor**：读取 PDF 书签识别章节层级
- **FormatBasedPdfExtractor**：分析文本格式（标题字号/权重）推断章节结构

### 第二步：预处理（Pre-Process）

清洗文本噪声、统一格式、处理特殊字符。

### 第三步：切分（Chunking）

**这是整个 RAG 系统中最关键的环节。** 如果切分做不好，后续检索质量无从谈起。

| 参数 | 推荐值 | 说明 |
|------|--------|------|
| Chunk 长度 | 200-400 Tokens | 政策/法律文档可达 600 Tokens |
| 切分边界 | 段落/句子 | 不截断句子，最好在段落间切分 |
| Chunk 重叠 | 10-20% | 避免关键信息落在边界上 |

**2025-2026 年分块策略汇总**：

| 策略 | 适用场景 | 特点 |
|------|----------|------|
| 固定大小 | 简单场景 | 最简单，但容易截断语义 |
| 递归分割 | 通用（LangChain 默认） | 按段落→句子→词的优先级逐级切分 |
| 语义分块 | 内容主题变化多 | 用 Embedding 计算相邻段落相似度，差异超阈值才分块 |
| **Late Chunking** | 复杂文档 | **新突破**：先整篇向量化再切分，每个块的向量「记得」整篇上下文。比传统分块准确率提高 15-30% |
| Contextual Retrieval | 长文档问答 | Anthropic 推荐：每个块前加文档级摘要 |

> 实战建议：先用递归分割跑起来，遇到效果不好的场景再换 Late Chunking 或 Contextual Retrieval。

### 第四步：生成元数据

为每个 Chunk 附加元数据，用途：
- **丰富 LLM 生成**：添加引用、页码信息
- **检索过滤**：支持自定义搜索和过滤

常见元数据字段：源文档名称、页码范围、章节路径、Chunk 序号/总数、引用编号、LLM 生成的摘要。

### 第五步：生成向量

- **稠密向量**：Embedding 模型生成。推荐将源文档名称和章节路径加入生成 Embedding 的文本中，增强语义相关性。使用 `BAAI/bge-small-en-v1.5`（384 维，CPU 可运行）
- **稀疏向量**：词项频率 + xxHash（无需维护词汇表）

### 第六步：存储

存入 Qdrant，在关键字段上建索引（文档名、Chunk 序号、章节路径），便于高效查询相邻 Chunk。

### 摄取调度

| 策略 | 适用 |
|------|------|
| 手动 | 数据很少变化 |
| 定时任务（每日） | 文档变化较频繁 |
| 事件驱动（实时） | 文档管理系统，源文档变化时立即触发 |

## 检索 + 生成

### 检索流程

用户查询经过与摄取管线类似的流程（预处理 → 向量化），但增加三个检索优化环节：

```
用户查询
  → 预处理 → 向量化（稠密+稀疏）
  → Qdrant 混合搜索（Embedding 70% + BM25 30%）
  → Top-k × 2（例如返回 10 个而非 5 个）
  → 扩展相邻 Chunk（命中 ±1-2 个索引）
  → Reranker 重排序 → 输出 Top 5
```

### 相邻 Chunk 扩展

搜索命中的 Chunk 前后 1-2 个 Chunk 极可能也相关。前提：元数据中保存了 Document Name、Chunk Index、Section Path。

### 重排序（Reranking）

检索结果中常有完全不相关的 Chunk，Reranker 做二次打分过滤。

**两种 Reranker 方案**：

| 方案 | 模型 | 特点 |
|------|------|------|
| Cross Encoder | `BAAI/bge-reranker-base` | 专用打分模型，比 LLM 快得多，CPU 可运行 |
| LLM Reranking | GPT-4.1 Mini 等轻量模型 | 灵活，但增加延迟。通过专用 system prompt（0-10 分制）评分 |

**投入产出比最高的优化**：加一层 Reranker 后准确率从 70% → 85%+。

## 生成（Generation）

### 上下文注入格式

最佳实践：使用 Tool message 注入检索结果。

```
System message → 规则：使用检索文档为唯一事实来源，引用来源，不行就说不知道
Tool message   → 检索到的 Chunks + 元数据（文档名/章节/页码）
User message   → 用户问题
```

### 模型选择

- **仅 RAG 功能**：低成本 LLM 足够（总结检索文档）
- **使用编排器**（LangChain / Semantic Kernel）：需要支持 Tool Calling 的模型
- 示例项目使用 Ollama + **Llama 3.2 3B**（CPU 可运行），更大模型通常更可靠

## 部署策略

### 微服务架构

每个服务独立部署，便于分别扩展：

```
┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐
│ Embedder │  │ Reranker │  │  Qdrant  │  │   LLM    │
│  (CPU)   │  │  (CPU)   │  │ (Docker) │  │  (GPU)   │
└──────────┘  └──────────┘  └──────────┘  └──────────┘
      ↑              ↑            ↑             ↑
      └──────────────┴────────────┴─────────────┘
                        │
               Container Orchestrator
                  (Kubernetes)
```

### 自托管 vs 云服务

| 组件 | 推荐方案 | 原因 |
|------|----------|------|
| Embedder | 自托管（开源模型，CPU 可运行） | 成本低，不需要 GPU |
| Reranker | 自托管（开源模型） | 同上 |
| 向量数据库 | Qdrant Docker 自托管 | 开源，运维简单 |
| LLM（生成） | **云服务** | GPU 需求高，云服务通常比自建 GPU 便宜 |

**混合方案最优**：轻量模型自托管，生成模型走云服务。

## RAG 五类方案选型速查

见 [[../concepts/rag-architectures|RAG 架构概念页]] 完整对比。本文额外补充两个新范式：

### PathRAG（路径感知图检索）

在知识图谱上找到从查询实体到答案实体的「路径」，沿路径信息作为上下文。适合供应链追溯、因果推理、路径类查询。

### Vectorless RAG（2026 新范式）

**完全抛弃向量数据库**。不切块、不向量化，让 LLM 直接「阅读」文档结构来推理定位信息。代表框架：PageIndex。

- **核心观点**：分块本身就是有损操作——层次结构、交叉引用、上下文关系、视觉排版全丢失
- **优势**：架构简单，保留完整上下文，适合复杂长文档
- **局限**：非常新、生态不成熟、LLM 调用成本高、不适合海量文档

## 混合架构实战推荐

生产系统不建议只选一种方案。推荐四步组合：

```
第一步：向量检索快速找到相关文档块（广撒网）
第二步：知识图谱补充关系信息（精准补全）
第三步：Reranker 重排序（推荐 BGE-Reranker）
第四步：LLM 综合生成回答
```

**向量数据库选型速查**：

| 数据库 | 定位 | 适用 |
|--------|------|------|
| Chroma | Python 原生，极简上手 | 学习/原型/小项目 |
| Qdrant | Rust 编写，高性能低延迟 | 中型生产系统 |
| Milvus | 企业级分布式，千亿级向量 | 大型企业系统 |
| Pinecone | 全托管 Serverless | 不想管服务器 |
| Weaviate | 语义+结构搜索 | 需要混合检索 |
| PGVector | PostgreSQL 插件 | 已有 PG 基础设施 |

**图数据库选型**：Neo4j（最主流，LangChain 原生支持，社区资源最多）> NebulaGraph（国产分布式）> TigerGraph（企业级）。
